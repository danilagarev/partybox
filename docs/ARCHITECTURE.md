# Техническая архитектура

Статус: рабочая основа. Решение: [ADR 0001](adr/0001-foundation.md).

## PB-055 — «Не может быть!»

Сценарий на 2–12 участников доступен локально и через rooms-v6. Dart ведёт
передачу общего телефона, TS авторитетно ведёт сетевую партию. Оба используют
версионированный JSON-набор. Выбор и порядок тем происходят в адаптерах,
правила получают готовую колоду. [ADR 0014](adr/0014-truth-and-protocol-v6.md).

## Актуальное дополнение PB-052

rooms-v5 добавляет закрытые личные голоса сетевого «Шпиона». Чистые TS-правила
считают результат после всех голосов; ничья создаёт новый тур среди лидеров.
Транзакция PostgreSQL сохраняет голоса и ack. Публичная проекция содержит только
прогресс, личная — собственный выбор. v1–v4 сохраняются для старых партий;
новая партия v5 требует обновления всех клиентов. [ADR 0013](adr/0013-spy-personal-voting.md).

## Актуальное дополнение PB-048

«Что объединяет?» добавляет offline Dart solo и авторитетный TS multiplayer
на1–12 участников через rooms-v4. Три игры имеют общий Flutter Web/Android/iOS
интерфейс. Production image содержит проверенную статику WEB_ROOT, доставленную
из точного CI artifact; Caddy обслуживает тот же origin для веба и API.
Решения и ограничения: [ADR0012](adr/0012-clues-and-shared-web.md). Ниже сохранена
история фундамента; упоминания «будущего» web/сети в раннем описании не заменяют
актуальные проверки STATUS.

## Границы

```mermaid
flowchart TD
  UI[Flutter: каталог и игровые экраны] --> Controller[Контроллер сессии]
  Controller --> Local[LocalSessionAdapter]
  Local --> Core[Чистый Dart game_core]
  Local --> Content[Встроенные JSON-наборы]
  Controller -. будущий онлайн .-> Remote[RemoteSessionAdapter]
  Remote -. HTTPS / Socket.IO .-> Server[NestJS: команды и персональные проекции]
  Server -.-> DB[(PostgreSQL)]
```

Сплошные связи — направление локальной реализации; пунктир — дальнейший этап.
LocalSessionAdapter и SpyController подключены к локальному игровому сценарию.
Адаптер выбирает локацию из неизменяемого набора фиксированной версии; контроллер
хранит сессию ядра и состояние показа карточки и доступности приложения.
Flutter-экран передаёт lifecycle и запускает обновления таймера, часы внедряются
в контроллер. Повтор партии сохраняет настройки в памяти. Для новой подготовки
после перезапуска приложение читает отдельный версионированный SpySetupStore;
конкретный SharedPreferencesAsync adapter подключается в main.

## Мобильное приложение

Flutter отвечает за Android/iOS, Material-тему и адаптивные экраны. Выбранный
«Полночный клуб» реализован в `src/design`: токены темы, компоненты, CustomPainter
и анимации входа без удержания предыдущей роли. Manrope и его лицензия включены
локально; системные Material-компоненты локализованы на русский. Минимальный web
host предназначен для локального превью, серверные возможности он не добавляет. `game_core`
не импортирует Flutter. UI вызывает команды ядра и рисует состояние; таймер не
уменьшает сохранённый счётчик каждую секунду, а вычисляет остаток по deadline.
Время передаётся ядру аргументом, чтобы фон/возврат и тесты не зависели от виджетов.

На старте достаточно небольших контроллеров на стандартных средствах Flutter.
Riverpod/GoRouter/Drift из беседы разумны при появлении асинхронной сессии, маршрутов
и persistence. Не подключаем Freezed и генераторы ради двух моделей.
Подход к разделению UI/data согласован с [рекомендациями Flutter](https://docs.flutter.dev/app-architecture/guide).

Секретный экран скрывается при inactive/paused и после явной передачи телефона.
Возврат из фона ведёт на закрытую карточку. Это UX-барьер: владелец одного телефона
технически контролирует всё локальное состояние; нельзя обещать криптографическую
изоляцию участников на общем устройстве.

## Правила и переиспользование

PB-031 добавляет вторую сетевую механику — «Шкалу терпения». Её чистые TS-правила
находятся в `games/tolerance.ts`; контент — отдельная авторская колода из 60 карточек.
RoomService сохраняет состояние игры в JSONB и строит публичную и личную проекции.
Протокол v3 добавляет `tolerance`/`privateTolerance`, сохраняя v1/v2. Общими остаются
комната, состав, авторизация, транзакции и ack. Фазы и очки обеих игр независимы;
универсальный движок не вводится. [ADR 0007](adr/0007-tolerance-and-protocol-v3.md).
У новой игры пока только сетевой режим; её правила в Dart-ядро не дублируются.

Первый модуль — «Шпион». Общее ядро минимально: игрок, фазы, выдача ролей,
закрытый результат и публичная проекция. Каждая игра может иметь собственный FSM;
не заставляем «Крокодила» и социальную дедукцию использовать одинаковые фазы.

В Dart и TypeScript правила выполняются отдельно. Общие вещи — JSON-схемы,
описание правил и затем JSON-векторы действий/ожидаемых состояний для обеих реализаций.
Для онлайн-версии серверные правила авторитетны. Клиент может показывать прогноз,
но не решает победу, роли, дедлайн или допустимость голосования.

## Сервер

Модульный монолит NestJS. `/health` независим от БД. Серверное лобби PB-040
реализовано через RoomController/RoomService/RoomRuntime: PostgreSQL, HTTP-команды
и персональные Socket.IO snapshots. RoomController/HttpRoomApi Flutter подключены
к полному сетевому циклу. GameRoomController обслуживает контракт v2; чистые TS-правила
находятся в games/spy.ts. Секретная сессия и readyIds сохраняются внутри комнаты
в JSONB, публичная и личная проекции строятся отдельно. Решения:
[ADR 0003](adr/0003-rooms-and-guests.md), [ADR 0005](adr/0005-network-spy.md).
Гость получает непрозрачный player token; PIN — способ найти комнату, не авторизация.
Секреты возвращаются только в личной проекции после проверки членства.

PostgreSQL хранит лобби, хеши гостевых токенов, регистрацию и подтверждения команд.
Состав комнаты заблокирован SELECT FOR UPDATE в транзакции. Миграция выполняется
отдельно; без DATABASE_URL сервер обслуживает health, комнаты отвечают 503.
TTL — 24 часа, явный выход передаёт ведущего по порядку входа; disconnect не меняет
состав. Время берётся сервером и внедряется в RoomService. Пока один процесс;
многопроцессная рассылка не реализована. Очистка истёкших комнат/ack/регистраций
и IP-счётчиков выполняется при старте и раз в минуту.

Для игровых команд применяется тот же порядок:
В транзакции: проверка версии → применение команды → новое состояние → сохранение
результата `commandId`. Рассылка после commit; при обрыве клиент запрашивает snapshot.
Отдельный event sourcing, Redis, брокер и микросервисы сейчас не нужны.

Socket.IO сохраняет порядок доставленных сообщений, но по умолчанию не гарантирует
повторную доставку. Поэтому ack, дедупликация и resync — наша ответственность:
[delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/).

## Контент и контракты

JSON-схема draft-07 с `schemaVersion`, `gameId`, `version`, `locale` и устойчивыми ID.
Версия набора фиксируется в партии, чтобы обновление не меняло активный раунд.
Встроенный JSON — первый источник; скачивание и store entitlement добавляются позже.
Общий встроенный каталог `game-content/spy-catalog.json` формата 1 фиксирует версии
трёх тем. Телефон и сервер читают его независимо. История локальных локаций живёт
в адаптере, сетевая — приватно в JSONB комнаты и атомарно обновляется с командой.
Ни каталог, ни ротация не требуют универсального движка. [ADR 0006](adr/0006-bundled-spy-catalog.md).
REST описываем OpenAPI при реализации API; realtime payload — отдельные JSON-схемы.
OpenAPI сам по себе не описывает весь двусторонний Socket.IO-протокол.

## Сборки и данные

Локальный режим работает без сервера. Имена, время и packId сохраняются одним
JSON-значением версии 1 через SpySetupStore; ключ `partybox.spy.setup`. Формат
проверяется до восстановления, ошибки не блокируют игру, удаление ограничено
собственным ключом. Сборка storage adapter находится в main, виджеты получают
интерфейс явно. Активный раунд держится только в памяти: роль, локация, seed и
deadline не записываются. После перезапуска доступна новая партия с прежней
подготовкой. Решение: [ADR 0002](adr/0002-local-setup-persistence.md). Перед аналитикой определяем события, согласие и retention.

CI сейчас проверяет поведение и статический анализ. Подписанные Android/iOS-сборки,
store-публикация появятся после выбора app ID и аккаунтов. Миграции и backend-деплой
уже автоматизированы отдельным production workflow (см. ниже).
iOS-сборка требует macOS/Xcode; локальная Linux-проверка Dart/Flutter её не заменяет.

## Мобильное лобби

RoomScreen → RoomController → HttpRoomApi (HTTP + Socket.IO) и RoomVault.
Этот сценарий не использует game_core и не меняет локальную игру. Каталог всегда
показывает обе игры и вход в комнаты. RoomServerSettings хранит только публичный
origin в SharedPreferences, ROOM_SERVER_URL служит значением по умолчанию.
Если адрес отсутствует, перед сетевым маршрутом открывается настройка подключения.
Release принимает HTTPS; смена адреса не переносит токен между серверами.
Доступ сохраняется отдельно в secure storage, с origin и retry-метаданными;
состояние комнаты не сохраняется. Lifecycle и возвращение на экран перечитывают
snapshot. Поздние ответы disposed-контроллера не меняют новый доступ.
Подробности и ограничения: [ADR 0004](adr/0004-mobile-room-access.md).

Общие векторы SpySession выполняются в Dart и TS. В сети readyIds допускают
параллельное подтверждение, затем адаптер применяет общие упорядоченные подтверждения
к ядру. Секретная карточка хранится только в памяти контроллера. Фон, disconnect,
команды и pop немедленно закрывают её. Сервер продвигает deadline при чтении и
фоновым проходом; после commit уведомляет все авторизованные соединения.

## Стенд физической приёмки

`deploy/compose.yaml`: приватный PostgreSQL → одноразовая миграция → read-only
backend от node user → Caddy с публичными 80/443. /ready проверяет БД/таблицы,
/health — жизнь процесса. TRUST_PROXY_HOPS=1 включён только за одним доверенным
прокси без прямой публикации backend; HTTP/Socket.IO используют один алгоритм IP.
Файловые секреты остаются вне image/Git; initializer идемпотентен. Локальный HTTPS
smoke использует отдельный CA и удаляемые volumes. [VPS](deploy/VPS.md).

## Production за отдельным Docker Caddy

`deploy/production` — отдельный Compose-проект со своей закрытой БД и API без
host-портов. Standalone Caddy пользователя вне Compose подключён к external
partybox_proxy и направляет partybox.sorima.tech → partybox-api:3000.
После успешного Checks выбранного main SHA пользователь вручную запускает
Deploy backend: build GHCR immutable image → SSH → migration/readiness/rollback.
Secrets SSH_* и DEPLOY_PATH соответствуют принятому процессу соседнего Baza;
папки/данные/сети приложений независимы. [ADR 0010](adr/0010-standalone-caddy-and-manual-cd.md),
[настройка владельцем сервера](deploy/PRODUCTION.md).
