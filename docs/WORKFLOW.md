# Рабочий процесс команды и агентов

Настроено 2026-11-21. Цель — завершённый проверяемый сценарий с небольшим
контекстом. Пользовательский план [Partybox-igry.md](../Partybox-igry.md) содержит
идеи; согласованные допущения конкретной реализации фиксируются в `docs/plans/`.

## Начало задачи

1. `git status --short`: определить пользовательские изменения и свои границы.
2. `node scripts/doctor.mjs` (для Flutter добавить `--mobile`, для обязательных
   БД-интеграций — `--database`). Диагностика показывает отсутствие инструментов,
   ничего не устанавливает. `FLUTTER_BIN` и `DART_BIN` поддерживают локальный SDK.
3. `node scripts/project-context.mjs backend` или другой модуль из подсказки CLI.
   Затем `rg -n` по именам функций/команд и чтение только нужных участков.
4. В многоэтапной задаче заполнить [шаблон плана](plans/TEMPLATE.md): полный сценарий,
   критерии, границы, допущения, проверка и передача. Сначала закрепить контракт.
   Шаблон постановки: `.github/ISSUE_TEMPLATE/task.yml`. При продолжении сначала
   читать «Передача работы» текущего плана.

[Граф проекта](PROJECT_GRAPH.md) — долговременный индекс файлов и зависимостей.
[STATUS](STATUS.md) — доказанные возможности и открытые проверки; ADR — причины
решений; план задачи — текущая передача. После перерыва читать нужные разделы,
а не всю историю. Код и результаты проверок имеют приоритет над памятью.

## Сабагенты и экономия контекста

Уточнено пользователем 2026-11-22: экономить токены выбором модели **после**
оценки сложности. Оценивать не число файлов само по себе, а неопределённость,
связность изменений, последствия ошибки и стоимость проверки.

| Сложность | Примеры и риск                                                               | Исполнитель                                                                                                   |
| --------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Низкая    | Точечный текст, поиск, форматирование, готовая фикстура                      | Обычно ведущий без делегирования. Если независимый пакет работы оправдывает агента — `gpt-6-luna`, low/medium |
| Средняя   | Изолированный экран/модуль, обычные тесты, разбор конкретного сбоя           | `gpt-6.2-sol`, medium; короткий контекст и конкретная приёмка                                                 |
| Высокая   | Неясная архитектура, приватность, транзакции/retry, совместимость протоколов | Решение ведущего; при необходимости независимый `gpt-6.2-astra`, high                                         |

Это рабочая маршрутизация доступных моделей, а не обещание цены или качества.
Проверять доступность модели в текущей сессии. При отсутствии выбранной модели
использовать доступную и явно отметить замену. Уже почти завершённого исполнителя
не перезапускать ради смены модели: повторная передача может стоить дороже.
После одного неудачного исправления оценить причину и при необходимости повысить
модель/контекст; не запускать бесконечные повторения дешёвого агента.

Для многоэтапной задачи использовать сабагентов, когда есть независимые области
или полезен независимый обзор; небольшое исправление выполнять одним агентом.
В этой среде до трёх работников и один ведущий, но число работников выбирать по
задаче. Сначала достаточно одного исследователя/ревьюера. Не запускать несколько
агентов читать один и тот же репозиторий целиком.

Контракт поручения: цель; нужные пути; разрешённые файлы; общий интерфейс;
критерии; команды проверок; результат до 15 строк с путями и воспроизводимыми
дефектами. Передавать минимальный контекст, без копии всей беседы. Один файл —
один редактор; изменения схем/генератора сначала согласуются с интегратором.
По умолчанию `fork_turns="none"`, с явными `model` и `reasoning_effort`, когда
интерфейс их поддерживает. Историю наследовать только при конкретной необходимости.
В плане достаточно одной строки на область: сложность → модель → файлы → приёмка.
Не создавать агента для подтверждения уже известного факта, координации или
повторного чтения того, что ведущий уже проверил. Доступные три слота — предел,
а не целевое число параллельных исполнителей.
Итоговую интеграцию и проверки проводит ведущий. Для существенного сетевого среза
попросить независимого агента проверить утечки, retry, восстановление и фазовые
переходы по коду и требованиям, без подсказки ожидаемых выводов.

Не загружать длинные успешные логи и generated-файлы без необходимости. Сначала
проверять изменённое поведение, затем обязательные проверки; повторять только
после изменения или сбоя. Не обещать измеренную экономию токенов без измерения.

Практический порядок проверки:

1. До передачи между слоями — анализ/контракт и узкие тесты изменённого поведения.
2. После интеграции — один общий прогон требуемых проверок. При сбое сначала
   повторять упавшие тесты; общий прогон повторять после финальных исправлений.
3. В плане сохранять краткую квитанцию: команда, результат, затронутый срез,
   путь к локальному логу. Успешный прогон без последующих изменений переиспользовать.
4. Flutter/Gradle запускать последовательно; один владелец блокировки. Проверки
   Node/PostgreSQL и независимый просмотр кода могут идти параллельно.

Вывод инструментов ограничивать: `rg` → нужный участок `sed`, успешные логи —
последние строки/счётчики, ошибки — точный контекст. Не перечитывать целые STATUS,
ARCHITECTURE и схемы на каждом шаге. Изменение Markdown не повод заново собирать APK.
Не добавлять MCP, фреймворк памяти или зависимости ради самого процесса;
использовать существующий граф и план. Координационные сообщения писать коротко
и с пробелами: плотные нечитаемые сводки увеличивают риск повторной работы.

## Инструменты и MCP

| Задача                          | Инструмент и граница                                                   |
| ------------------------------- | ---------------------------------------------------------------------- |
| Код и память репозитория        | `rg`, Git, CLI карты; внешняя memory DB не требуется                   |
| Изменяемая внешняя документация | Доступный web search, открытые первоисточники; сохранять ссылки и дату |
| UI и жесты Flutter web          | Playwright по соответствующему skill; устройство проверяется отдельно  |
| Макет Figma                     | Figma MCP при доступном подключении и конкретном макете                |
| GitHub issue/PR/Actions         | GitHub MCP при подключении; локальная работа возможна без него         |
| Схемы и типы                    | Генератор `game-contracts`, затем серверные и Dart-проверки            |

Установка MCP не является результатом задачи. Подключать сервер, когда ему есть
конкретный запрос, понятны права и нужен внешний источник. Сначала проверить
доступные инструменты/плагины; отсутствие соединения честно отметить. Не добавлять
неиспользуемые серверы и не переносить токены или приватное игровое состояние
во внешнюю память. Доступ к MCP зависит от клиента, а не от Markdown-файла.
Локальный Serena подготовлен в `scripts/serena.sh`, настройки проекта и индекс
памяти — `.serena/`. Подключение, границы и оценка пользы —
[AI_DEVELOPMENT](AI_DEVELOPMENT.md). При недоступном MCP продолжать через CLI/rg.
Глобальные настройки пользователя этот pipeline не меняет.

Публичный OpenAI Docs MCP проверен запросом `initialize` 2026-11-21:
сервер `openai-docs-mcp` ответил протоколом 2025-06-18. Переносимый
[пример подключения](mcp.example.toml) не содержит ключей; его секцию можно
добавить в настройки Codex на рабочей машине. Автоматического подключения в
этой сессии нет: `.codex` доступен только для чтения. Для Flutter/Socket.IO
использовать их официальную документацию через web; OpenAI MCP обслуживает
документацию OpenAI. Browser CLI Playwright доступен в окружении, использует
тот же набор браузерных действий, что и Playwright MCP.

## Завершение

`npm run check`, `make check-mobile` по затронутым модулям; для сети обязательны
интеграции с `TEST_DATABASE_URL` и полный цикл нескольких клиентов. В отчёте
различать пройденные, пропущенные и невозможные проверки. Перед сдачей обновить
STATUS/план и карту при изменении связей, выполнить `git diff --check` и
`node scripts/project-context.mjs --check`. Коммит/публикация — по поручению.

## От задачи до production

1. Задача содержит сценарий, критерии приёмки и границы. Новая ветка от main,
   например `feat/PB-056-workflow`; пользовательские изменения сохранить.
2. Реализация и узкие проверки. Для риска приватности/сети — независимое ревью.
3. Общие проверки через `node scripts/run-check.mjs node|mobile|release` по
   затронутым областям. Runner сохраняет логи/квитанции в `output/checks/`, не
   сокращает проверки и не кеширует успех. Пропуски смотреть в логе. Сверить diff.
4. Когда commit/push поручены: индексировать только файлы задачи явными путями,
   `git diff --cached --stat` и `git diff --cached --check`, затем commit с PB-ID.
   Пуш feature-ветки → PR по шаблону → ревью. Секреты в аргументы не передавать.
5. `Checks` на PR: Node/PostgreSQL, Flutter, production web, HTTPS/Docker smoke.
   После успешного ревью merge в main запускает отдельный push Checks. Результат
   PR не заменяет проверку merge commit. Не включать skip/fail-open ради скорости.
6. Успешный push Checks main запускает `Deploy backend`: точный SHA, артефакт
   прошедшей HTTPS-проверки попытки, image digest, production environment, SSH,
   миграция, readiness и внешний smoke. Отмена/ошибка CI не запускает деплой.
   Состояние проверять через GitHub Actions, а не по наличию YAML в локальной ветке.
7. Ручной workflow_dispatch с ранее проверенным SHA — redeploy/rollback;
   [runbook](deploy/PRODUCTION.md). Image rollback не отменяет SQL-миграции.

Однократная внешняя настройка: secrets production, инфраструктура VPS и защита
main (required checks `node`, `flutter`, `https`, обязательный PR, запрет force push).
Для production environment ограничить deployment branches веткой main;
required reviewers включать только если нужен ручной барьер каждого deploy.
Без них полностью автоматический CD требует успешного CI, но не отдельного клика.
Эти настройки не создаются коммитом YAML; при аудите 2026-11-23 защиты main не было.

Перед паузой/новой сессией: 10–20 строк в плане — цель, изменённые пути, решения,
проверки с логами, следующий шаг и препятствия. Не записывать содержимое логов и
историю беседы. Успешные результаты переиспользовать только для неизменных
исходников/окружения; fingerprint runner не покрывает SDK/БД/ignored-файлы.

## Основания выбора

Это прикладная адаптация проверенных 2026-11-21 первоисточников, а не утверждение
об универсально лучшем процессе:

- [OpenAI: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md):
  короткие постоянные правила и маршрутизация к нужным файлам.
- [OpenAI: skills](https://learn.chatgpt.com/docs/build-skills): загрузка подробных
  процедур по потребности. Переносимый [skill](../skills/partybox-delivery/SKILL.md)
  читается по ссылке; для автоматического обнаружения нужен `.agents/skills/`.
  В текущем sandbox `.agents` доступен только для чтения, поэтому установки туда нет.
- [OpenAI: subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents):
  независимые области и короткие сводки; параллельные записи требуют координации.
- [OpenAI: MCP](https://learn.chatgpt.com/docs/extend/mcp): соединения с внешними
  системами по конкретной потребности.
- [Anthropic: context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents):
  выборка контекста по ходу работы и короткие сохраняемые заметки.
