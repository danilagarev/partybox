# ADR 0009: каталог игр, адрес комнат и production-деплой

Статус: принято для PB-042, 2026-11-21. Production topology и trigger заменены
[ADR 0010](0010-standalone-caddy-and-manual-cd.md) после уточнений пользователя;
навигация/настройки остаются действующими.

## Контекст

Пользователь не нашёл вторую реализованную игру в APK: каталог содержал только
«Шпиона», а «Шкала терпения» выбиралась внутри лобби. Вход в комнаты зависел
от build URL. Теперь пользователь также поручил подготовить CI/CD на существующий
VPS рядом с другим backend, за Nginx, и дать пошаговую настройку поддомена.

## Решение: навигация

Каталог всегда показывает две равноправные игровые карточки с числом игроков,
характером игры и доступными телефонами. Затем идут правила и выбор режима.
«Шпион» сохраняет локальный сценарий; «Шкала» ведёт в комнату с выбранной игрой.
Вход/возврат по коду — общее действие. Серверная активная партия имеет приоритет
над выбором каталога, новое enrollment при восстановлении не выполняется.
Общий guard исключает двойное открытие при асинхронной настройке/загрузке.

ROOM_SERVER_URL остаётся значением по умолчанию. Пользователь может сохранить
другой origin в настройках подключения, без новой сборки. В shared_preferences
записывается только нормализованный публичный origin отдельным ключом
`partybox.rooms.server.v1`; токены по-прежнему принадлежат RoomVault. Запрещены
credentials, query, fragment, путь и некорректный порт; release принимает HTTPS.
Неверное сохранение не подменяется молча другим build URL. При смене origin
старый RoomVault не перезаписывается: прежняя проверка SERVER_CHANGED требует
явного удаления доступа либо возврата к старому адресу.

## Решение: production

Новый комплект `deploy/production/` независим от локального HTTPS-комплекта.
Docker-проект `partybox_prod` имеет собственные сеть/volume/секреты; backend
привязан к loopback:3100. Существующие приложение и порты Nginx 80/443 не заменяются.
UID/GID deploy-пользователя задаются при инициализации, секреты сохраняются
идемпотентно с правами 600. Backend остаётся непривилегированным и read-only.

GitHub Actions workflow_run принимает успешный push Checks собственного main.
Checkout и образ привязаны к проверенному SHA; перед отправкой проверяется
актуальность main. Деплой использует immutable GHCR digest и SSH с проверенным
known_hosts. Права токена ограничены чтением содержимого/записью пакета;
runtime-секреты не проходят через Actions. Environment production хранит только
доступ деплоя. Параллельные обновления сериализуются в Actions и flock на VPS.

Миграция предшествует замене backend. Ошибка миграции оставляет прежний backend;
неуспешная readiness нового образа возвращает предыдущий. Данные БД не удаляются,
rollback не откатывает SQL. Будущие миграции должны сохранять совместимость
со старым образом либо идти отдельным согласованным процессом.

## Последствия

Требуется однократная настройка DNS/TLS/Nginx, deploy-пользователя, SSH host key,
доступа GHCR и GitHub Environment. [Инструкция](../deploy/PRODUCTION.md) содержит
перечень Secrets/Variables. SSH, DNS и реальный сервер в этой итерации не меняются.
Публичный туннель не нужен: новый постоянный поддомен настраивает владелец VPS.
Конфигурация настроек поддерживает этот адрес в уже установленном приложении.

Приняты штатные возможности [GitHub workflow_run](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run),
[Docker Compose](https://docs.docker.com/compose/how-tos/networking/) и
[Nginx WebSocket proxy](https://nginx.org/en/docs/http/websocket.html).
Локальные Docker-тесты не считаются реальным GitHub/VPS-развёртыванием.
