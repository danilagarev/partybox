# ADR 0003 — комнаты и гостевой доступ

Дата: 2026-11-08. Статус: принято для серверного лобби PB-040.

## Контекст

Пользователь выбрал комнаты и онлайн для «Шпиона» следующим этапом. Срок комнаты
и поведение ведущего согласованы: 24 часа с создания; явный выход передаёт
управление следующему оставшемуся участнику по порядку входа; обрыв связи
не меняет состав и ведущего. PIN позволяет войти новым участником, но не восстановить
чужое место. Активная локальная партия не переносится на сервер.

## Решение

PostgreSQL хранит комнаты, участников, результаты команд и регистрацию гостей.
Изменения одной комнаты сериализуются блокировкой строки в транзакции; ack
сохраняется в той же транзакции. Повторы проверяются до expectedVersion.
Состав — 1–12 участников в лобби, для старта игры потребуется минимум 4.
После явного выхода токен не даёт читать комнату или вернуться прежним участником.
Последний выход закрывает комнату; удалённые участники не возвращаются автоматически.

Гость получает непрозрачный bearer token. В БД — только SHA-256 токена.
Создание/вход содержат requestId и retryKey (32 случайных байта base64url): это
позволяет безопасно повторить запрос при потерянном ответе. Токен воспроизводится
через HMAC-SHA-256 стабильным серверным ROOM_TOKEN_SECRET. В БД остаются только
хеш retryKey, fingerprint запроса и ссылки на комнату/участника. Секрет сервера
должен переживать рестарт, его смена меняет выдаваемые при повторе токены, поэтому
ротация потребует отдельного протокола. Срок токена ограничен сроком комнаты.

HTTP отвечает за команды и snapshot. Socket.IO аутентифицирует соединение токеном
и отправляет персонально построенный snapshot. После reconnect всегда читается
актуальное состояние; буферизованное восстановление чужих событий не применяется.
Один процесс backend; межпроцессная рассылка до горизонтального масштабирования
не реализуется. Истечение срока проверяется серверными часами на каждом доступе.

PIN — шесть случайных цифр. Попытки создания/входа и чтения ограничиваются по IP
в БД, независимо от существования PIN; X-Forwarded-For не доверяем автоматически.
Размер JSON и Socket.IO payload ограничен. Секреты и тела запросов не логируются.
Схемы версии 1 — источник типов и совместимых примеров. В лобби privateState=null;
полное внутреннее состояние никогда не сериализуется в ответ.

## Последствия

Без БД health работает, комнаты возвращают явную недоступность. Миграции выполняются
отдельной командой до запуска, не на каждом запросе. В CI нужна PostgreSQL.
Для первого сервера принимается один процесс; масштабирование, очистка по retention,
мобильное хранение токена и игровая серверная машина состояний требуют следующих
срезов. Комнаты логически истекают через 24 часа; физическая очистка отдельная.

## Технические источники

Транзакция выполняется на одном pg client — [node-postgres](https://node-postgres.com/features/transactions).
Конкурентное изменение комнаты сериализует блокировка строки —
[PostgreSQL](https://www.postgresql.org/docs/16/explicit-locking.html).
Socket.IO подключается к HTTP-серверу —
[официальная документация](https://socket.io/docs/v4/server-initialization/).
